## Bloque 049A-1 — Fase 2 S8: cola — reintento manual único (UI Sincronización)

- **Test nuevo** `cola_reintento_manual_uno_error_visible_sin_auto_flush`
  (`tests/bdp_push.rs`). Escenario del plan: fila pendiente → reintento manual único → error
  visible → sin auto-flush → estado por ítem correcto. El mecanismo real de la UI
  Sincronización es `reintentar_uno`; la modalidad se fija a `manual` en la config.
- **Diseño honesto al guard fail-closed (H-W-2):** un 5xx deja la intención `ambiguo` en
  `bdp_audit_log` y `authorize` bloquea el reenvío de la entidad hasta reconciliar la
  intención (anti-duplicación correcto; la reconciliación automática solo existe en el
  poller de `create_order`). Por eso el reintento manual se ejercita sobre un rechazo
  **4xx definitivo** (auditoría `error`, no `ambiguo`, sin bloqueo anti-duplicación):
  - **1)** flush automático (sin forzar) en modalidad `manual` → `omitidos_manual=1`,
    `procesados=0`, **cero** llamadas HTTP (sin auto-flush);
  - **2)** `reintentar_uno` contra un BDP que rechaza (422) → fila `rechazado` con error
    visible (status 422, cuerpo redactado [287A-4]), `reintentos=0` (4xx no consume),
    auditoría `error` (nunca `ambiguo`), **una** llamada HTTP;
  - **3)** re-edición local (encolar de nuevo con el dato corregido, M19) refresca la fila
    `rechazado` → `pendiente` (vuelve a la cola activa);
  - **4)** el flush automático sigue sin tocarla (`omitidos_manual=1`, cero llamadas);
  - **5)** `reintentar_uno` con el BDP aceptando (200) → `sincronizado`, la fila sale de la
    cola activa, auditoría `exito`, **una** llamada HTTP (total 2 en todo el test).
- **H-W-2 queda documentado como limitación:** el reintento tras `ambiguo` exige reconciliar
  la intención (runbook manual — verificar en BDP si se aplicó, marcar resuelta, reintentar);
  el camino manual sin bloqueo es el de `rechazado` + re-edición, que es el que demuestra S8.
- Suite `bdp_push`: **17/0** (16 previos + 1 nuevo). Sin líneas de depuración residuales.

## Bloque 049A-1 — Fase 3 W-Q2.1: INCIDENTE 200109 (alta real de artículo web) + fix local sync_catalog fallback

### Contexto y causa raíz

- La primera escritura real autorizada de Fase 3 (W-Q2.1: alta de prueba `90000003` "PRUEBA W1
  2026-09-05" con `WebArticle:true`, filas `f67fdb0b`, `64df3746`, `791502c5` estado
  `sincronizado`) se aplicó correctamente en el BDP real vía `CreateArticlesAndUpdateProfiles`
  (AllProfiles:true). Antes del alta, ExportArticles devolvía `Articles: []` sin error (cero
  artículos web).
- **Consecuencia:** `90000003` es el **primer y único artículo web** del BDP real → ExportArticles
  pasa de "vacío sin error" a "encuentra 1 y falla validación" →
  `[200109]-ALGUNO DE LOS ARTÍCULOS CONTIENE ERRORES DE VALIDACIÓN` (HTTP 200 con ErrorMessage,
  propagado como `Remote`). `sync-catalog` quedó roto para siempre (HTTP 500) porque:
  - **No existe DeleteArticle** en el contrato WebLink;
  - la neutralización vía `ModifyArticleAndUpdateProfile` (`WebArticle:false`) falló con **NRE
    determinista** del BDP real (ver abajo).

### Neutralización agotada: NRE del endpoint Modify (BDP real)

- El endpoint `ModifyArticleAndUpdateProfile` del BDP real devuelve **NRE determinista**
  ("Referencia a objeto no establecida como instancia de un objeto.") con el payload mínimo de la
  app (~8 campos ArticleData; el manual exige ~100), en todas las variantes probadas:
  - Variante 1: `AllProfiles:true` + ProfilesList ausente → NRE (2 intentos, fila
    `0e98d796-a3a9-40a6-b338-ddac935123da` con WebArticle:false);
  - Variante 2: `AllProfiles:false` + ProfilesList `[{Profile:1,ProfileName:"PERFIL 1"}]` (patrón
    del manual) → NRE (1 intento);
  - **Control:** Modify `90000000` (NO existe en el BDP real) con la misma estructura → NRE (fila
    `e9013114-ebe7-4424-866d-7bfcd4b94adc`).
- **Conclusión diagnóstica:** la NRE NO es específica de `90000003`; el endpoint Modify del BDP
  revienta con el payload mínimo tanto con artículo existente como inexistente, mientras que
  `create` con el mismo payload sí funciona. **Nunca ha habido un `modify_article` exitoso
  contra el BDP real** (auditoría). Hipótesis: el Modify deserializa el payload mínimo a su
  objeto interno completo (~100 campos) y revienta con una referencia nula.
- **Verificado post-escrituras:** `sync-catalog` seguía HTTP 500/200109 tras todas las escrituras
  (2 remediación + 1 control) → **el BDP NO mutó** con ninguna escritura de remediación.

### Decisión del usuario y fix local

- Con la neutralización **bloqueada por el BDP**, el usuario eligió **fix local `sync_catalog`
  fallback** (opción recomendada): restaurar sync-catalog funcional dejando `90000003` como está
  (web, sin más escrituras BDP). Antes el fix local era contraproducente (se podía neutralizar);
  ahora es la única vía para restaurar sync-catalog (si no, quedaría roto 200109 para siempre).
- **Cambio** en `src/services/bdp_sync.rs::sync_catalog`:
  - Si `export_articles` devuelve error cuyo mensaje contiene `[200109]` → ya NO aborta: loguea
    `warn!` y deja `articles` vacío para que entre el fallback de perfil H-Q1-03 existente
    (`list_profile_articles` → GetPOSList, catálogo operativo de items, ~557 artículos).
  - Solo el error `[200109]` cae al fallback; cualquier otro error de ExportArticles (red, HTTP,
    parseo) sigue abortando para no enmascarar problemas reales.
  - **Caso borde fail-closed:** variable `export_fallo_200109` distingue el motivo. Si fue
    `[200109]` (sabemos que hay un artículo web roto) y el perfil también devuelve vacío →
    `return Err` (no cerrar verde con 0 ocultando la corrupción). El vacío legítimo de
    ExportArticles + perfil vacío conserva el `info!` + continuar original (sin regresión).
  - `cargo check` OK vía `node scripts/run-cargo.mjs`.
