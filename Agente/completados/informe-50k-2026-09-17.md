## Qué frena (techo medido, no hipotético)

- El origen aguanta **~210-230 DYNAMIC/s**. Por encima, pg satura (~1 núcleo:
  69-106 % CPU con 8/10 conexiones del pool activas) y el p50 de listados
  pasa de ~200 ms a ~700-800 ms. El pool (10) NO es el cuello (nunca se agota).
- Causa por query: `ventas_listar`/`gastos_listar` ~14 ms (Index Scan Backward +
  filtro + ordenación sobre 17k filas) y SUMs del dashboard ~14-15 ms (Seq Scan,
  correcto a este tamaño). 230/s × ~10-15 ms ≈ 1 núcleo.
- El contenedor app nunca es el cuello: CPU ~150 % de 400 % disponibles,
  RSS 1,2-1,57 GB de 7,7 GB (ver nota memoria).
- El borde no falla nunca: 0 errores en todos los tramos; el origen encola
  en vez de romper (CF absorbe, HITs siempre servidos).
- T1/T2 no se repitieron: con Tmax el contenedor ya iba sobrado (150 %/400 %);
  constreñirlo solo bajaría el techo que ya fija postgres. Decisión registrada,
  no medición omitida por pereza.
